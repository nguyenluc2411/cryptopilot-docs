# CLAUDE.md – Operating Rules for AI Coding Agents

Project: CryptoPilot – Crypto Trading Support System (capstone 09/2026 – 03/2027).
CryptoPilot is a decision-support and paper-trading system. It never executes real orders, never uses exchange API keys, never holds funds, never gives investment advice.

## 1. Read order at the start of every session

0. **Pull the documents first**: `./docs.sh pull` (Windows: `.\docs.ps1 pull`), then `git pull`. The documents below live in a second repository over this same folder (`docs/BOOTSTRAP.md`), so without this they are whatever this machine last saw — a `NEXT` marker somebody has already moved, a decision that has since changed. Everything in this list is read out of files that another member may have written since.
1. `CLAUDE.md` (this file)
2. `CURRENT_STATE.md` → find the task marked `NEXT`, its dependencies, acceptance criteria and open questions
3. `docs/design/TECHNICAL_DESIGN.md` → only the sections referenced by the task
4. SRS (`docs/srs/`) → the BR, UC, NSF, SCR and MSG ids referenced by the task
5. `docs/design/CryptoPilot_Logical_Model.txt` when the task touches data

## 2. Mandatory codebase analysis (before writing any code)

Do all of the following and summarize the findings in 5–10 lines before implementing:
1. List the projects/folders touched by the task and read the existing files in them.
2. Find existing abstractions to reuse (value objects, base classes, ports, test builders). Do not duplicate them.
3. Check `CURRENT_STATE.md` sections "Decisions" and "SRS Alignment" for rules that change the SRS.
4. Run the full test suite once and record the baseline (passed/failed counts).
5. Identify every BR/UC/NSF the task implements and the tests that must prove them.

## 3. Execution rules

- Work on exactly one task (the `NEXT` task) per session unless the user says otherwise. Execute all its phases autonomously (analysis → implementation → tests → docs → state update) without asking for confirmation.
- If a business rule is ambiguous or contradicts another source: do NOT guess. Implement what is unambiguous, add the question to "Open Questions" in `CURRENT_STATE.md` with the task id, and mark the task `BLOCKED` or `PARTIAL`.
- Follow the priority of sources in TECHNICAL_DESIGN section 0.
- After every checkout or rebase, run `./mvnw clean verify`, never plain `verify`: `target/classes` keeps the migrations of the previous branch and Flyway applies them, which fails tests that are not broken.
- Every public domain calculation must have XML doc comments including `<remarks>` with the rule id and the academic/technical reference. Cite SRS ids, and where useful the id of a private document (`TECHNICAL_DESIGN 7.1`, `ADR-011`, `D-45`, `Q-16`, `A-33`); never copy text out of a private document (section 9), because code is committed and those documents are not, e.g.:

```csharp
/// <summary>Computes the Wilder RSI incrementally for one closed candle.</summary>
/// <remarks>
/// Rule: BR-12.
/// Reference: Wilder, J. W. (1978). New Concepts in Technical Trading Systems. Trend Research.
/// </remarks>
```

## 4. DO NOT

- Do not implement real order placement, exchange account linking, or any use of exchange API keys.
- Do not use `double`/`float` for prices, quantities or money (see TECHNICAL_DESIGN 5.4). Indicators are the only exception.
- Do not use `DateTime.Now`/`DateTime.UtcNow` directly; inject `IClock`.
- Do not put business logic in controllers, hubs, EF configurations or Hangfire job classes; they only orchestrate.
- Do not reference Infrastructure or EF Core from Domain or Application.
- Do not write to another module's tables (TECHNICAL_DESIGN section 2).
- Do not add NuGet/npm/pub packages that are not in TECHNICAL_DESIGN 1.3 without adding an ADR and a Decisions entry. Never add MediatR, AutoMapper or FluentAssertions v8+.
- Do not hard-code secrets, URLs of environments, LLM model names or thresholds that exist in `system_setting`.
- Do not edit an EF Core migration that has already been merged to `develop`.
- Do not change a BR formula in code. Proposed changes go to "SRS Alignment" and need team approval.
- Do not skip, delete or weaken tests to make the build pass. Do not lower coverage gates.
- Do not suppress analyzer warnings without a justification comment and a task id.
- Do not leave `TODO` without a task id (`// TODO(T-042): ...`).
- Do not commit `.env`, credentials, real user data or generated build output.
- Do not add "Generated by", "Co-Authored-By" or any AI attribution to commits, pull requests, code, comments or docs.
- Do not stage, commit or push a local-only file (section 9). Never use `git add -f` / `--force`, `git commit --no-verify` or `-n`, and never edit `.git/info/exclude` or the hooks.
- Committed files may cite private documents **by id only**: a section number of TECHNICAL_DESIGN, an ADR id, or a D-xx, Q-xx or A-xx id, next to the SRS ids (BR/UC/NSF/SCR/MSG) and task ids. Do not quote, paraphrase at length or paste content from any private document (SRS text, TECHNICAL_DESIGN, ADR, CURRENT_STATE.md, CLAUDE.md) into committed files, commit messages or pull requests — write the rule in your own words in the code, or cite the id. Do not link to the documents repository or name local-only paths (`docs/design/…`, `docs/srs/…`) in committed files.
- Do not `git push` unless the user asks for it in the current session; commit locally and let the user review first.
- A pull request into `develop` does not close its issues: `Closes #x` acts only on the default branch (`main`). After the merge, close each issue by hand with a comment that names the PR and the merge commit.
- Do not refactor code outside the scope of the current task.

## 5. Coding standards

- Backend: .NET (see ADR-002), C# with `Nullable` enabled and `TreatWarningsAsErrors`; file-scoped namespaces; one type per file; async all the way with `CancellationToken`.
- Naming: use case folder `Application/<Module>/Commands/<UseCase>/`; test names `<RuleId>_<Scenario>_<Expected>`.
- Backend packages (D-48, the rule for every module and every new class):
  - `service/` holds interfaces. A new service is always two files: `service/FooService.java` (interface, only the methods callers outside the class use) and `service/impl/FooServiceImpl.java` (`@Service`, `@Transactional` and the other annotations live here). Inject `FooService`, never `FooServiceImpl`; tests construct the impl directly and mock the interface.
  - A bean that implements a port declared in `client` or in another module (e.g. `PersistentBinanceBans implements BinanceBanStore`) goes in `service/impl/` and needs no second interface.
  - Helpers and components are not services: every class that is not an interface — `@Service` implementations, helper `@Component`s such as `AccessTokenIssuer`, `LatestMarketData`, `SymbolSyncWriter`, and pure helpers such as `ExchangeSymbolMapper` — lives in `service/impl/`. The rule and its only exception (`auth.service.LiveSessions`) are in "Service đặt ở đâu" below.
  - Classify every record before writing it: accepted by a controller → `dto/request/`; returned by a controller → `dto/response/`; never crosses the API (service, job, repository and client results) → `model/`; the shape of an external API (Binance, VNPay …) → the module's `client/` package. No record in `service/` or `service/impl/`.
  - A DTO never depends on `entity`; the enums it needs come from `model/enums/` (rule `dtos_doNotDependOnEntities`). A class of `market.client` is not used outside `market`.
- Errors: return `Result`/`Error` with a stable code that maps to an SRS message code (MSGxx).
- Web: TypeScript strict; feature folders; server state in TanStack Query; decimals from API kept as strings and formatted with a decimal library.
- AI Service: TypeScript strict; validate every input with zod; no database access.

### Enum đặt ở đâu

- Top-level enum: `<module>/model/enums`, có `package-info.java` với `@NamedInterface("enums")`.
- Enum chỉ có nghĩa trong 1 class: lồng trong class đó.
- Ngoại lệ: `common.exception.ErrorCode`.
- Tạo module mới có enum: nhớ tạo `package-info.java`, nếu không `ModularityTest` sẽ fail khi module khác dùng enum đó.
- `PackageConventionTest.enums_resideInModelEnums` kiểm tra quy tắc này.

### Service đặt ở đâu

- `..service` chỉ chứa interface; class hiện thực và helper nội bộ nằm trong `..service.impl`.
- Ngoại lệ duy nhất: `com.cryptopilot.auth.service.LiveSessions`, vì `auth.config` (`JwtConfig`, `SessionLivenessValidator`) inject nó; giữ làm ngoại lệ, không tách interface (team lead, 2026-09-30).
- Một job được inject helper trong `service.impl` của chính module (ví dụ `MarketStreamSupervisor` → `LatestMarketData`); controller thì không bao giờ.
- Javadoc `{@link}` tới một class không tính là phụ thuộc khi phân loại.
- `PackageConventionTest.servicePackages_holdOnlyInterfaces` kiểm tra quy tắc này; ngoại lệ mới phải ghi tên đầy đủ trong rule kèm lý do.

## 6. Definition of Done (per task)

1. Acceptance criteria in `CURRENT_STATE.md` are met.
2. Unit tests for every referenced BR, including boundary cases; integration tests for any DB or external adapter change.
3. All tests pass locally; architecture tests pass; coverage gates hold.
4. No new analyzer warnings; formatting applied (`dotnet format`, `eslint --fix`, `dart format`).
5. OpenAPI updated for API changes; TECHNICAL_DESIGN updated if the design changed.
6. `CURRENT_STATE.md` updated with the session block (section 8).
7. Commits follow section 7.

## 7. Commits

Conventional Commits, English, imperative:

```
feat(trading): add liquidation price calculator with bracket maintenance amount

Implements BR-26, BR-27, BR-28.

Refs: T-061
```

Types: feat, fix, test, refactor, perf, docs, build, ci, chore, style, revert. Scope = module name in lower case. Subject ≤ 72 characters. One logical change per commit. No attribution trailer of any kind. The local `commit-msg` hook rejects messages that break these rules; if it rejects a commit, fix the message — never bypass the hook.

## 8. Session end – append this block to `CURRENT_STATE.md` → "Session Log" (newest first)

```
### YYYY-MM-DD – T-xxx <task title>
- Result: DONE | PARTIAL | BLOCKED
- Summary: <what was built, 2–4 lines>
```

Then update the task row status, move the `NEXT` marker to the next task whose dependencies are DONE, and update "Last updated" at the top of `CURRENT_STATE.md`.

## 9. Local-only files and git hygiene

These paths exist only on developers' machines. They are listed in `.git/info/exclude` (local to each clone, never committed) by `docs/tools/setup-local.sh` or `setup-local.ps1`:

```
CLAUDE.md  CLAUDE.local.md  CURRENT_STATE.md  .claude/
docs/README.md  docs/srs/  docs/design/  docs/adr/  docs/test/  docs/tools/
```

- You may read and update them freely (CURRENT_STATE.md is updated every session), but they never enter a commit.
- Two local hooks enforce this: `pre-commit` blocks local-only paths, `.env` files and attribution text in staged lines; `commit-msg` blocks attribution and non-Conventional subjects.
- Before every commit run `git status --short` and confirm that only source files of the current task are staged.
- The product integrates an LLM provider, so words such as "anthropic" or "claude" may legitimately appear in AI Service code (SDK, model configuration). Only attribution is forbidden, not the product domain.
